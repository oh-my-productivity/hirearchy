# F-read experiment: why a reviewer with `read` cannot open the writer's file

> Repeatable form: `tests/integration/test_real_kiro.py::test_builtin_read_reads_the_org_but_not_outside` (opt-in, `pytest --run-integration`).

Question (study E, finding F3): in a documents org every agent holds kiro's built-in `read`, confined to the user's
input folder. The writer's memo lives in `lead/writer/work/`; the reviewer could not read it, and the agents said
"the @orgmcp/read tool does not appear as a callable function". Is orgmcp's `read` hidden behind the built-in one
(name collision), or present but misused? Does adding the org root to the built-in `read`'s `allowedPaths` fix it?

Setup: kiro-cli 2.29.1, `claude-haiku-4.5`, a throwaway org `/tmp/orgmcp-fread-<ts>/org` made with this worktree
(`uv run orgmcp --root ... init / hire / task / run --once`). Agents `a` and `c`, `b` only holds a file:
`b/work/memo.md` = `ORGFILE-SECRET-222`; `inputs/in.txt` = `INPUT-SECRET-111`. `a` = `tools: [read]`, `inputs: [<S>/inputs]`
(exactly the E-study shape); `c` = no tools. Four runs in total (logs in `evidence/`).

## Conclusions

1. **It is a name collision, not misuse.** An agent that holds the built-in `read` sees exactly one tool named `read`
   (kiro's); orgmcp's `read` is not callable. Without the built-in (run 2) the same name `read` is orgmcp's
   (`Running: @orgmcp/read`). The prompt told such agents "org files are read with `@orgmcp/read`, never with the
   built-in `read`", i.e. to use a tool they cannot call. The same holds for `write` (study D, F1: built-in `write`
   shadows orgmcp `write`); not touched here.
2. **The built-in `read` was refused on the org because the profile denied it**: `deniedPaths` = org dir (a hard deny,
   even for kiro's own "cwd is readable" rule). So the agent had no working way to read a teammate's file.
3. **Allowing the org for the built-in `read` works** (runs 3 and 4), but it must be an allow plus *no* deny on the
   org (a deny beats the allow). Paths must be absolute: a relative path resolves in the agent's working directory
   (its own org folder, or its workspace), not at the org root.
4. Everything else stays confined: `/etc/hosts` is still refused (run 4); built-in `write` keeps the org deny.

## Fix (see the commits)

* `scheduler.file_confinement`: the built-in `read` gets workspace + inputs + the org root (`P` and `P/**`) and no deny;
  `write` unchanged (workspace only, org denied). The profile name carries a hash of the settings, so every
  existing confined profile gets a new name and file on the next run of its agent (old files are left, they are
  inert; legacy global profiles and legacy unconfined charters are untouched).
* Prompt (`core._files_lines`, a `core.py` change outside the assigned files, kept to those lines): agents with
  the built-in `read` are told it hides `@orgmcp/read`, and that it reads org files by ABSOLUTE path `<org root>/<path>`.
* Plan: "can read files only in X and the organization's own files".
* Validator: `verifier-cannot-read` also covers authors that leave their work in the org folder; it asks the real
  `file_confinement` whether the verifier's `read` can open the org (so the old profile would make it fire).

## Safety

`~/.kiro/agents/*` and `~/.kiro/settings/mcp.json` md5s before and after: identical (`evidence/safety-before.txt`,
`safety-after.txt`; the file contents were never printed). The four profiles with `ORG_ROOT` = the sandbox org were
deleted; no process referenced the sandbox when the experiment ended; the sandbox directory was removed.
